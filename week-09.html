Basics: OpenFlow, concretely

Before P4, OpenFlow defined a standard way for a controller to program a switch. Knowing its objects makes every later idea (P4 tables, verification, telemetry) easier.

The cast of messages

Anatomy of a flow entry

A rule has a match (ingress port, Ethernet and IP fields, ports, VLAN, ...), a priority (the highest matching rule wins), counters (packets and bytes), instructions or actions (output, drop, rewrite, push a tag, go to the next table, apply a group or meter), timeouts (idle and hard: soft state again) and a cookie the controller uses to identify its rules. Since OpenFlow 1.1 a packet passes through a pipeline of tables; each table's instructions may send it to a later table, which avoids the cross-product of rules that a single table would need (e.g. VLAN × ACL × routing). Group tables implement multipath ('select' buckets, the hardware form of ECMP) and fast failover (a group tries its first live bucket). Meters rate-limit.

A learning switch as an SDN application

The classic first application: when a Packet-In arrives, record that the source MAC lives on the ingress port; if the destination MAC is known, install a rule and forward, otherwise flood. The controller's program is ten lines; the cost is the control-channel round trip for the first packet of every flow and a table entry for every active pair. Lab 9.7 counts both, and shows why production designs install rules proactively and aggregate them (per destination or per prefix).

Why sketches and filters appear everywhere in data planes

A switch has tens of megabytes of fast memory and a nanosecond-scale budget per packet, so it cannot keep an exact record for millions of flows or addresses. A Bloom filter answers 'have I seen this item?' using a few bits per item at the price of occasional false positives and no false negatives. It is the simplest example of the trade that sketches make: exchange exactness for small, fixed memory. Lab 9.5 verifies the false-positive formula; the demo below lets you size one.

Basics: three planes of a network

Every network device does three different jobs. The data plane moves packets: parse the header, look up a table, forward, at nanosecond timescales in hardware. The control plane computes the tables: routing protocols, spanning tree, ARP. The management plane configures devices and monitors them (CLI, SNMP, NETCONF). In traditional routers all three live in one closed box, and a new feature means waiting for the vendor.

What 'software-defined' means

Software-defined networking (SDN) separates the control plane from the data plane: switches become simple, fast forwarders and a (logically) centralised controller computes global policy and installs rules via a southbound API (OpenFlow, P4Runtime, gNMI). Applications such as traffic engineering, access control and virtual networks sit on top via a northbound API. Benefits: a global view makes optimisation and verification feasible; network behaviour becomes software that can be tested and versioned.

Match-action: one abstraction for everything

A switch table is a list of rules; each rule has a match (header fields, possibly with wildcards or prefixes), an action (forward to port, drop, rewrite a field, set a queue, send to the controller) and a priority. Routers, firewalls, NATs and load balancers all reduce to match-action tables. The first lab implements a tiny interpreter of this idea.

Reactive versus proactive control

In reactive mode the first packet of a flow goes to the controller, which installs a rule: flexible but adds latency to flow setup and load to the controller. In proactive mode rules are pre-installed from policy, which scales and survives controller failure. Production systems are mostly proactive with centralised optimisation on a slower timescale.

What P4 adds

OpenFlow fixed the set of header fields a switch could match. P4 is a language to define the parser, the match-action tables and the deparser themselves, so a switch can support new protocols, tunnels or telemetry without new silicon. A P4 program has three parts: a parser (a state machine extracting headers from bytes), match-action control blocks (tables and actions), and a deparser (reassembling the packet).

// Sketch of a P4_16 ingress block (illustrative, not a complete program)
table ipv4_lpm {
    key = { hdr.ipv4.dstAddr : lpm; }
    actions = { forward(); drop(); }
    default_action = drop();
}
apply { if (hdr.ipv4.isValid()) ipv4_lpm.apply(); }

Why SDN

Traditional routers bundle control and forwarding in closed boxes. OpenFlow (McKeown et al. 2008) exposes a table of match-action rules and a logically centralised controller computes them, so network-wide policy (traffic engineering, slicing) is software. Google's B4 WAN runs near 100% link utilisation with SDN-based traffic engineering versus 30-40% typical in conventional WANs.

Match-action and P4

A switch pipeline parses headers, matches against tables (exact, ternary, longest-prefix) and applies actions (forward, rewrite, drop, meter). P4 (Bosshart et al. 2014) makes the parser and tables programmable, so new protocols or telemetry need no new silicon. Trade-offs: controller scalability and failure, consistent updates, and limited per-packet compute and memory.

Measurement with sketches

Switches cannot keep per-flow counters for millions of flows. A count-min sketch (Cormode and Muthukrishnan 2005) uses d hash rows of w counters; an update increments one counter per row and the estimate is the minimum, which never underestimates. With w = ⌈e/ε⌉ and d = ⌈ln(1/δ)⌉ the overestimate is at most εN with probability 1−δ.

In this run the error falls about 2.5x per doubling of width (faster than the worst-case 1/w bound, because the Zipf stream is dominated by a few heavy flows), and the top flows are estimated to within 1% with 4,096 counters per row.

Consistent network updates

Changing many switches' rules one by one can create transient loops or black holes. Reitblatt et al. (2012) proposed per-packet consistent updates by two-phase commit: install the new rules tagged with a new version on the internal switches first, then flip the ingress switches to stamp packets with the new version, and finally remove old rules. Every packet is processed entirely by the old or the new configuration, never a mix.

Network verification

Because configurations are code, they can be checked. Header Space Analysis (Kazemian et al. 2012) treats packet headers as bit vectors and rules as transformations to answer reachability and loop questions; Batfish (Fogel et al. 2015) analyses router configurations offline. Verification finds bugs like unintended reachability or missing route filters before deployment.

Virtualised network functions

NFV moves firewalls, NATs and load balancers from appliances to software on commodity servers (Sherry et al. 2012 argued for outsourcing middleboxes). Challenges: per-packet cost at 100 Gb/s (DPDK, kernel bypass, SmartNICs), state migration during scaling, and service chaining. eBPF/XDP now processes packets inside the Linux kernel at tens of millions of packets per second per core group.

The programmable pipeline, in numbers

A switch ASIC such as a 12.8 Tb/s chip handles billions of packets per second in a fixed number of match-action stages; each stage has limited SRAM/TCAM, so telemetry must be compressed (sketches) and rules aggregated. In-band network telemetry (INT) lets each hop append queue depth and timestamps to a packet, giving per-hop latency visibility.

Common pitfalls

Treating the controller as always available, forgetting TCAM limits (a ternary entry costs about twice the bits of an exact entry), and updating rules without ordering guarantees.

Advanced: switch architecture and its limits

A programmable pipeline (e.g. PISA: Protocol-Independent Switch Architecture) consists of a programmable parser, a fixed number of match-action stages (tens), each with limited SRAM and TCAM and a few ALUs, then a deparser, with a traffic manager (queues, schedulers) in the middle. Because every packet passes each stage in one clock, there are no loops: a program must fit in the stage count, and state is limited to registers, counters and meters with restricted read-modify-write per packet. This is why measurement uses compact data structures. An exact-match table in SRAM costs the key width, a ternary (TCAM) rule costs about twice the key width in bits plus higher power, and longest-prefix match uses algorithmic tries or TCAM; table capacity is typically hundreds of thousands to a few million entries.

Advanced: telemetry and sketching

In-band network telemetry (INT) lets each hop append metadata (switch ID, queue depth, timestamps) to a probe or data packet, enabling per-hop latency decomposition; sinks aggregate and export. Sketches summarise streams in sublinear memory: count-min for frequency (never underestimates; additive error ≤ εN with probability 1−δ for w = ⌈e/ε⌉, d = ⌈ln 1/δ⌉), count sketch for unbiased estimates, Bloom filters for membership, HyperLogLog for distinct counts, and universal sketches for many metrics at once. Sketches are mergeable across switches (element-wise addition when hash functions match) and across time. The third lab shows a precision-recall trade-off: narrow sketches over-estimate many mice and produce false heavy hitters; wide ones recover both.

Advanced: network update and verification

Consistent updates (Reitblatt et al. 2012) give per-packet consistency by version-tagging; later work makes updates faster using ordering (dependency graphs), incremental updates, and time-based updates with synchronised clocks. Verification checks properties of the network: Header Space Analysis represents sets of packets as wildcard bit vectors and rules as transfer functions; VeriFlow and NetPlumber check each update incrementally in microseconds to milliseconds; Batfish builds a model of router configurations to answer reachability and policy questions before deployment; Minesweeper and later tools encode control-plane behaviour in SMT. P4 verification (p4v, Vera) checks the programs themselves. Practical lesson: most outages come from configuration, so test and verify the network the way software is tested.

Advanced: network functions and in-network computing

NFV runs firewalls, NATs, load balancers (Maglev, Katran), DPI and proxies as software on commodity hardware. High-performance packet I/O uses DPDK (user-space polling), eBPF/XDP (programs in the kernel receive path, handling tens of millions of packets per second per few cores) and SmartNICs/DPUs (offload flow tables). Programmable switches have been used for in-network key-value caching (NetCache, SOSP 2017), aggregation for ML training (SwitchML, NSDI 2021), consensus acceleration and load balancing, trading severe memory limits for line-rate speed. Operating SDN at scale also needs management interfaces: model-driven configuration (YANG with NETCONF/gNMI), streaming telemetry, intent-based abstractions, and controllers such as ONOS or OpenDaylight with replicated state for fault tolerance.

Advanced: a complete P4 program, line by line

The listing below follows the structure of the standard P4_16 tutorial programs for the v1model architecture (BMv2). It is shown for study and was not compiled in this build.

#include <core.p4>
#include <v1model.p4>
const bit<16> TYPE_IPV4 = 0x800;
typedef bit<9>  egressSpec_t;  typedef bit<48> macAddr_t;  typedef bit<32> ip4Addr_t;
header ethernet_t { macAddr_t dstAddr; macAddr_t srcAddr; bit<16> etherType; }
header ipv4_t {
    bit<4> version; bit<4> ihl; bit<8> diffserv; bit<16> totalLen; bit<16> identification;
    bit<3> flags; bit<13> fragOffset; bit<8> ttl; bit<8> protocol; bit<16> hdrChecksum;
    ip4Addr_t srcAddr; ip4Addr_t dstAddr; }
struct metadata { }
struct headers { ethernet_t ethernet; ipv4_t ipv4; }

parser MyParser(packet_in packet, out headers hdr, inout metadata meta, inout standard_metadata_t sm) {
    state start { transition parse_ethernet; }
    state parse_ethernet { packet.extract(hdr.ethernet);
        transition select(hdr.ethernet.etherType) { TYPE_IPV4: parse_ipv4; default: accept; } }
    state parse_ipv4 { packet.extract(hdr.ipv4); transition accept; }
}
control MyVerifyChecksum(inout headers hdr, inout metadata meta) { apply { } }
control MyIngress(inout headers hdr, inout metadata meta, inout standard_metadata_t sm) {
    action drop() { mark_to_drop(sm); }
    action ipv4_forward(macAddr_t dstAddr, egressSpec_t port) {
        sm.egress_spec = port; hdr.ethernet.srcAddr = hdr.ethernet.dstAddr;
        hdr.ethernet.dstAddr = dstAddr; hdr.ipv4.ttl = hdr.ipv4.ttl - 1; }
    table ipv4_lpm { key = { hdr.ipv4.dstAddr: lpm; } actions = { ipv4_forward; drop; NoAction; }
                     size = 1024; default_action = drop(); }
    apply { if (hdr.ipv4.isValid()) { ipv4_lpm.apply(); } }
}
control MyEgress(inout headers hdr, inout metadata meta, inout standard_metadata_t sm) { apply { } }
control MyComputeChecksum(inout headers hdr, inout metadata meta) {
    apply { update_checksum(hdr.ipv4.isValid(),
        { hdr.ipv4.version, hdr.ipv4.ihl, hdr.ipv4.diffserv, hdr.ipv4.totalLen, hdr.ipv4.identification,
          hdr.ipv4.flags, hdr.ipv4.fragOffset, hdr.ipv4.ttl, hdr.ipv4.protocol, hdr.ipv4.srcAddr, hdr.ipv4.dstAddr },
        hdr.ipv4.hdrChecksum, HashAlgorithm.csum16); } }
control MyDeparser(packet_out packet, in headers hdr) { apply { packet.emit(hdr.ethernet); packet.emit(hdr.ipv4); } }
V1Switch(MyParser(), MyVerifyChecksum(), MyIngress(), MyEgress(), MyComputeChecksum(), MyDeparser()) main;

Reading it. The header types define byte layouts exactly as Lab 9.4's struct.unpack does. The parser is a state machine: it extracts the Ethernet header, branches on etherType, and extracts IPv4. MyIngress holds the match-action logic: a table keyed on the destination address with longest-prefix matching whose actions rewrite the MAC addresses, set the output port and decrement the TTL; the controller fills the table at run time through P4Runtime. MyComputeChecksum recomputes the header checksum after the TTL change (hardware often uses the incremental update shown in Lab 9.4). The deparser re-serialises the valid headers. A header never extracted stays invalid and is not emitted, which is how tunnels are added or removed: extract the outer header and do not emit it.

Advanced: stateful processing and what fits in a pipeline

A register array stores per-index state that a packet can read, modify and write back within one stage, enabling per-flow counters, sketches (a count-min row is one register array indexed by a hash), meters and simple state machines such as TCP flag tracking. Constraints decide what is feasible: a packet touches each register at most once in the pipeline; the arithmetic is integer, with limited ops; recirculation (sending the packet through the pipeline again) buys extra passes at the cost of throughput; and the stage count (a dozen to a few tens) bounds dependent steps. This is why algorithms must be redesigned for the data plane: HULA keeps the best next hop per destination ToR using probes rather than flow state; heavy-hitter detectors keep a small 'candidate' table next to a sketch; and in-network aggregation (SwitchML) streams fixed-size vectors through a pool of accumulators.

Advanced: the cost of telemetry

In-band telemetry adds metadata to packets: with k hops and h bytes of metadata per hop the added bytes are about a header plus k·h (e.g. 5 hops × 16 B = 80 B, 5.3% of a 1,500-byte packet and 55% of a 150-byte one). Operators therefore sample (mark one packet in N), use postcards (each switch exports its own report rather than stacking it in the packet) or export only on events such as a queue exceeding a threshold or a packet drop (mirror-on-drop). The collector must handle millions of reports per second, so filtering and aggregation in the data plane (Bloom filters and sketches again) are part of the design.

Advanced: header-space analysis and what verification costs

Lab 9.6 treats each rule as a transfer function on sets of headers. Real tools represent these sets as unions of wildcard expressions (HSA), binary decision diagrams or SMT formulas, and answer reachability, loop, black-hole and isolation questions. Complexity comes from rewrites (NAT, tunnels) and from the number of rules; tools reach millions of rules by computing equivalence classes of packets that are treated identically (VeriFlow, APV) and by processing updates incrementally. Control-plane verification (Batfish-like) goes one level up: it models the routing protocols to predict the forwarding tables from the configuration, catching errors before deployment. Limits: models of vendor behaviour may be incomplete, dynamic behaviour (failures, timing, convergence) is harder than static snapshots, and verification proves only the properties you state.

Advanced: controller architecture and scale

A production controller is a distributed system: a replicated, consistent store for network state (ONOS and OpenDaylight use clustering with consensus or eventually consistent stores for different data), southbound drivers for many device types, northbound APIs, and application logic. Typical goals: tens of thousands of devices, sub-second reaction to failures, no single point of failure. Design principles drawn from operations: keep the data plane able to forward without the controller (fail-static); reconcile intended versus actual state continuously rather than trusting every message; version and roll out network changes like software with staged rollout and automatic rollback; and monitor the controller's own latency. Management protocols have converged on gNMI/gRPC with YANG models and streaming telemetry instead of polling SNMP.

Advanced: SDN and the limits of centralisation

Centralisation gives a global view but adds a control-loop latency of milliseconds to seconds, so reflexes (fast reroute, link-failure detection with BFD, load balancing per flowlet) stay in the data plane or on the device, while slow optimisation (traffic engineering, capacity planning, policy) lives in the controller. This hybrid, a logically centralised, physically distributed control plane, is the pattern in Google's Jupiter and B4, in cloud virtual networks (the controller pushes encapsulation and filtering rules to host virtual switches such as Open vSwitch or custom smart NICs) and in enterprise intent-based systems.

Lab 9.1: A match-action switch

A tiny interpreter for prioritised wildcard rules, the abstraction behind OpenFlow and P4 tables. Fields not mentioned in a rule are wildcards.

rules = [  # (priority, match dict, action)
    (300, {"proto": "tcp", "dport": 22}, "drop"),
    (200, {"dst": "10.1.2.0/24"}, "port3"),
    (100, {"dst": "10.0.0.0/8"}, "port1"),
    (0,   {}, "send_to_controller"),
]
def ip(a): x = [int(v) for v in a.split(".")]; return (x[0] << 24) | (x[1] << 16) | (x[2] << 8) | x[3]
def in_prefix(addr, pre):
    base, l = pre.split("/"); l = int(l); m = (0xFFFFFFFF << (32 - l)) & 0xFFFFFFFF
    return ip(addr) & m == ip(base) & m
def matches(pkt, m):
    for k, v in m.items():
        if k == "dst":
            if not in_prefix(pkt["dst"], v): return False
        elif pkt.get(k) != v: return False
    return True
def forward(pkt):
    return next(a for pr, m, a in sorted(rules, key=lambda r: -r[0]) if matches(pkt, m))
for pkt in ({"dst": "10.1.2.7", "proto": "udp", "dport": 53}, {"dst": "10.9.9.9", "proto": "tcp", "dport": 80},
            {"dst": "10.1.2.7", "proto": "tcp", "dport": 22}, {"dst": "8.8.8.8", "proto": "udp", "dport": 53}):
    print(pkt, "->", forward(pkt))
Output

Lab 9.2: Consistent updates: naive versus two-phase

Four switches A, B, C, D. The old routes are A→B→C→D; the new ones are A→C→B→D. Updating the switches one at a time in every possible order exposes transient loops; version-tagging (two-phase) never does.

from itertools import permutations
old = {"A": "B", "B": "C", "C": "D"}
new = {"A": "C", "B": "D", "C": "B"}
def reaches(table, src, dst="D"):
    seen, n = set(), src
    while n != dst:
        if n in seen or n not in table: return False
        seen.add(n); n = table[n]
    return True
bad = 0
for order in permutations("ABC"):
    t = dict(old); ok = True
    for sw in order:
        t[sw] = new[sw]
        ok = ok and all(reaches(t, s) for s in "ABC")
    bad += not ok
    print("update order", "".join(order), "-> transient loop/blackhole:", not ok)
print(f"{bad} of 6 orders break connectivity; two-phase update: every packet follows a complete old or new path:",
      reaches(old, "A"), reaches(new, "A"))
Output
update order ABC -> transient loop/blackhole: False
update order ACB -> transient loop/blackhole: True
update order BAC -> transient loop/blackhole: False
update order BCA -> transient loop/blackhole: False
update order CAB -> transient loop/blackhole: True
update order CBA -> transient loop/blackhole: True
3 of 6 orders break connectivity; two-phase update: every packet follows a complete old or new path: True True

Lab 9.3: Heavy-hitter detection with a count-min sketch

Detect flows carrying at least 0.5% of 200,000 packets with a 4-row sketch of increasing width; report precision and recall against ground truth.

import random
from collections import Counter
random.seed(5); n_flows, N = 5000, 200000
stream = random.choices(range(n_flows), [1 / (i + 1) for i in range(n_flows)], k=N)
true = Counter(stream); thr = 0.005 * N
hh = {f for f, c in true.items() if c >= thr}
def detect(w, d=4):
    ab = [(random.randrange(1, 10**9), random.randrange(10**9)) for _ in range(d)]
    t = [[0] * w for _ in range(d)]
    for x in stream:
        for j, (a, b) in enumerate(ab): t[j][(a * x + b) % 1000003 % w] += 1
    est = lambda f: min(t[j][(a * f + b) % 1000003 % w] for j, (a, b) in enumerate(ab))
    found = {f for f in true if est(f) >= thr}
    tp = len(found & hh); return tp / max(1, len(found)), tp / len(hh)
print("true heavy hitters:", len(hh))
for w in (64, 256, 1024, 4096):
    pr, rc = detect(w); print(f"width {w:5d}: precision {pr:5.1%}  recall {rc:5.1%}")
Output

width   256: precision 78.6%  recall 100.0%

Lab 9.4: From bytes to headers: parsing IPv4 and updating the checksum

A programmable parser extracts headers from raw bytes; a data-plane step decrements the TTL and fixes the checksum. The sample header is the standard Wikipedia example (checksum 0xb861). The incremental update is RFC 1624: HC' = ~(~HC + ~m + m').

import struct
def csum(data):
    s = sum(struct.unpack("!%dH" % (len(data) // 2), data))
    while s >> 16: s = (s & 0xFFFF) + (s >> 16)
    return (~s) & 0xFFFF
hdr = bytes.fromhex("450000730000400040110000c0a80001c0a800c7")      # checksum field zeroed
c = csum(hdr); print("computed header checksum:", hex(c), "(known answer 0xb861)")
pkt = bytearray(hdr); pkt[10:12] = c.to_bytes(2, "big")
print("checksum over the finished header (must be 0):", csum(bytes(pkt)))
def parse_ipv4(b):
    v_ihl, tos, tot, ident, ff, ttl, proto, ck, src, dst = struct.unpack("!BBHHHBBH4s4s", b[:20])
    return dict(version=v_ihl >> 4, ihl=v_ihl & 15, total_len=tot, ttl=ttl, proto=proto, src=".".join(map(str, src)), dst=".".join(map(str, dst)))
print(parse_ipv4(bytes(pkt)))
old = (pkt[8] << 8) | pkt[9]; pkt[8] -= 1; new = (pkt[8] << 8) | pkt[9]       # forward: TTL - 1
hc = int.from_bytes(pkt[10:12], "big")
s = (~hc & 0xFFFF) + (~old & 0xFFFF) + new
while s >> 16: s = (s & 0xFFFF) + (s >> 16)
inc = (~s) & 0xFFFF
z = bytearray(pkt); z[10:12] = b"\x00\x00"
print("incremental checksum:", hex(inc), "| full recomputation:", hex(csum(bytes(z))), "| equal:", inc == csum(bytes(z)))
Output
computed header checksum: 0xb861 (known answer 0xb861)
checksum over the finished header (must be 0): 0
{'version': 4, 'ihl': 5, 'total_len': 115, 'ttl': 64, 'proto': 17, 'src': '192.168.0.1', 'dst': '192.168.0.199'}
incremental checksum: 0xb961 | full recomputation: 0xb961 | equal: True

Lab 9.5: Bloom filters: measured versus theoretical false-positive rate

A Bloom filter of m bits and k hash functions holds n items with false-positive rate (1 − e^(−kn/m))^k. Insert 20,000 items, then query 50,000 items that were never inserted.

import hashlib, math
class Bloom:
    def __init__(self, m, k): self.m, self.k, self.bits = m, k, bytearray(m)
    def _idx(self, x):
        h = hashlib.sha256(str(x).encode()).digest()
        a, b = int.from_bytes(h[:8], "big"), int.from_bytes(h[8:16], "big") | 1
        return [(a + i * b) % self.m for i in range(self.k)]            # double hashing
    def add(self, x):
        for i in self._idx(x): self.bits[i] = 1
    def __contains__(self, x): return all(self.bits[i] for i in self._idx(x))
n = 20000
print("bits/item  k   measured FPR   theory")
for b in (4, 8, 12, 16):
    m = n * b; k = max(1, round(b * math.log(2))); f = Bloom(m, k)

    print(f"{b:9d} {k:3d} {fp:12.4%} {(1 - math.exp(-k * n / m)) ** k:10.4%}")

Lab 9.6: A miniature header-space analysis: finding a forwarding loop

Packet headers are 8-bit strings over {0,1,x}. Each switch has ordered match rules. We propagate the set of headers that match each rule along the network and flag paths that revisit a switch. This is the core idea of Header Space Analysis.

def inter(a, b):
    out = []
    for x, y in zip(a, b):
        if x == "x": out.append(y)
        elif y == "x" or x == y: out.append(x)
        else: return None
    return "".join(out)
net = {"A": [("1xxxxxxx", "B"), ("0xxxxxxx", "C")],
       "B": [("11xxxxxx", "D"), ("10xxxxxx", "A")],        # bug: headers 10xxxxxx bounce back to A
       "C": [("xxxxxxxx", "D")],
       "D": [("xxxxxxxx", "deliver")]}
def explore(node, hs, path, found):
    if node == "deliver": found.append(("delivered", path, hs)); return
    for match, nxt in net[node]:
        h = inter(hs, match)
        if h is None: continue
        if nxt in path: found.append(("LOOP", path + [nxt], h)); continue
        explore(nxt, h, path + [nxt], found)
found = []; explore("A", "xxxxxxxx", ["A"], found)
for kind, path, hs in found: print(f"{kind:9s} {'->'.join(path):16s} headers {hs}")
Output
delivered A->B->D->deliver headers 11xxxxxx
LOOP      A->B->A          headers 10xxxxxx
delivered A->C->D->deliver headers 0xxxxxxx

Lab 9.7: Reactive versus proactive rule installation

200 hosts generate 20,000 random flows. A reactive controller installs an exact-match (source, destination) rule for each new pair via Packet-In and Flow-Mod; a proactive controller pre-installs one rule per destination.

import random
random.seed(11); H, F = 200, 20000
seen = set(); packet_in = 0
for _ in range(F):
    s, d = random.randrange(H), random.randrange(H)
    if s != d and (s, d) not in seen: seen.add((s, d)); packet_in += 1
print(f"reactive exact-match: {packet_in} Packet-In/Flow-Mod pairs, {len(seen)} table entries")
print(f"proactive per-destination: 0 Packet-Ins, {H} entries ({len(seen) / H:.0f}x smaller table)")
print("all-pairs exact entries for 2,000 hosts:", 2000 * 1999)
print("control-channel load at 10,000 new flows/s with 128-byte Packet-Ins:", 10000 * 128 * 8 / 1e6, "Mb/s")

rules = [("10.0.0.0/8", "port1"), ("10.1.0.0/16", "port2"), ("10.1.2.0/24", "port3"), ("0.0.0.0/0", "drop")]
def ip(s): a = s.split("."); return sum(int(x) << (24 - 8 * i) for i, x in enumerate(a))
def lpm(addr):
    best = None
    for pre, act in rules:
        base, l = pre.split("/"); l = int(l); mask = (0xFFFFFFFF << (32 - l)) & 0xFFFFFFFF if l else 0
        if ip(addr) & mask == ip(base) & mask and (best is None or l > best[0]): best = (l, act)
    return best[1]
for a in ("10.1.2.7", "10.1.9.9", "10.200.0.1", "8.8.8.8"): print(a, "->", lpm(a))

import random
random.seed(3); w, d = 256, 3
ab = [(random.randrange(1, 10**9), random.randrange(10**9)) for _ in range(d)]
h = lambda j, x: (ab[j][0] * x + ab[j][1]) % 1000003 % w
def sketch(stream):
    t = [[0] * w for _ in range(d)]
    for x in stream:
        for j in range(d): t[j][h(j, x)] += 1
    return t
A, B = [1, 2, 2, 3] * 50, [2, 4, 4, 4] * 50
SA, SB = sketch(A), sketch(B); M = [[a + b for a, b in zip(r1, r2)] for r1, r2 in zip(SA, SB)]
est = lambda S, x: min(S[j][h(j, x)] for j in range(d))
print("merged estimate of flow 2:", est(M, 2), "  true:", (A + B).count(2))
print("merged equals sketch of concatenation:", M == sketch(A + B))

Exercises

Exercise 1: Choose CMS dimensions for ε = 0.001, δ = 0.01.

w = ⌈e/0.001⌉ = 2719, d = ⌈ln 100⌉ = 5, i.e. about 13,600 counters.

Exercise 2: Name two drawbacks of a logically centralised controller.

Single point of failure/scalability and added control latency; mitigated by replicated, distributed controllers and proactive rule installation.

Exercise 3: Why are count-min sketches mergeable across switches?

With identical hash functions the counter arrays are linear: adding two sketches element-wise gives the sketch of the combined stream, so a controller can merge per-switch sketches.

Exercise 4: In a two-phase update, why must internal switches be updated before the ingress?

If ingress stamped the new version first, packets would reach internal switches lacking rules for it and be dropped.

Exercise 5: Heavy hitters: flows > 1% of N = 10⁶ packets. A sketch with ε = 0.001 overestimates by at most how much?

εN = 1000 packets (w.h.p.), so a 10,000-packet threshold is reliable.

Exercise 6: A ternary 5-tuple rule (104 bits) needs how many TCAM bits?

About 2 × 104 = 208 (two bits per ternary bit).

Exercise 7: A Bloom filter holds n = 1,000,000 items in 10 bits per item with k = 7 hash functions. Memory and false-positive rate?

m = 10⁷ bits = 1.25 MB; FPR ≈ (1 − e^(−0.7))⁷ = 0.5034⁷ ≈ 0.82%.

Exercise 8: A reactive controller handles 10,000 new flows/s with 128-byte Packet-Ins. Control-channel bandwidth?

10,000 × 128 × 8 = 10.24 Mb/s (plus the Flow-Mods back), and every flow's first packet pays a controller round trip.

Exercise 9: 2,000 hosts, exact-match all-pairs rules. Entries needed versus per-destination rules?

2,000 × 1,999 ≈ 4.0 million versus 2,000.

Exercise 10: A ternary 5-tuple rule uses 104 key bits. How much TCAM do 1 million such rules need?

About 2 × 104 = 208 bits each → 208 Mbit ≈ 26 MB, far beyond typical TCAM capacities, so rules must be aggregated or kept in SRAM-based tables.

Exercise 11: Why must an incremental checksum update use the old and new 16-bit word?

The checksum is a one's-complement sum, so replacing a word m by m' changes it by (m' − m): HC' = ~(~HC + ~m + m').

Exercise 12: Why do the 10xxxxxx headers loop in the header-space lab?

Switch B sends them back to A, and A forwards all headers starting with 1 to B again.

Key takeaway

CMS error ≤ ε·N with prob. 1−δ ; w=⌈e/ε⌉, d=⌈ln 1/δ⌉
