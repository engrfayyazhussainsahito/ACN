Basics: the transport mechanisms underneath, from first principles

This section builds the vocabulary needed for the rest of the chapter, assuming only that you know what a packet is.

Reliability from scratch

Suppose a sender wants to deliver ten packets over a network that may lose, duplicate or reorder them. The sender numbers each packet; the receiver replies with acknowledgments (ACKs) saying what has arrived; the sender keeps a copy of anything unacknowledged and retransmits it after a timeout. Stop-and-wait sends one packet per round trip: on a 100 ms path that is ten packets per second, no matter how fast the link. To use the pipe, the sender needs a window: many packets in flight at once. TCP uses a cumulative ACK ('I have everything up to byte N'), plus optional selective ACKs (SACK) naming extra ranges. QUIC uses ranges from the start.

Timers: what to wait for

Wait too short and you retransmit packets that were merely slow (wasting capacity and shrinking the window); wait too long and a loss stalls the connection. So the timeout must track the path's round-trip time and its variation. Both TCP and QUIC keep a smoothed RTT (a moving average with weight 1/8 on each new sample) and an RTT variance (weight 1/4) and set the timeout to roughly smoothed RTT plus four times the variance. Lab 6.4 implements QUIC's version.

Window-limited throughput

The sender may have at most one window of data outstanding, so throughput ≤ window / RTT. A default 64 KB window over a 100 ms path caps throughput near 5 Mb/s; filling a 1 Gb/s, 100 ms path needs a window of 12.5 MB, the bandwidth-delay product. This is why receive buffers must be tuned (Lab 6.6 prints the table) and why a lost window-sized burst is expensive.

Cryptography without the mathematics

You need three facts. (1) A symmetric cipher encrypts bulk data quickly with a shared secret key. (2) A key exchange such as Diffie-Hellman lets two parties who have never met create a shared secret by exchanging public values that an eavesdropper cannot turn into the secret; Lab 6.5 runs it with tiny numbers (p = 23, g = 5 gives shared secret 2). (3) A signature lets the server prove it owns a public key that a certificate authority has vouched for. HKDF is the standard tool that stretches a shared secret into many independent keys (one per direction and purpose), distinguished by textual labels.

A packet on the wire

A QUIC packet is a UDP datagram. The first byte's top bit says long header (handshake) or short header (data). A short header carries just the flags, the destination connection ID (so the receiver can find the connection even if the sender's IP address or port changed) and a packet number; the rest is encrypted payload made of frames. QUIC's integers use a variable-length encoding in which the two top bits of the first byte select a 1, 2, 4 or 8 byte representation, so small values cost one byte; Lab 6.3 decodes the examples from the specification and shows how a stream ID's two low bits encode who started the stream and whether it is one-way.

Self-check

How long does stop-and-wait take to send 100 packets over a 50 ms RTT path? (100 × 50 ms = 5 s.) Why must the timeout depend on RTT variance as well as the mean? Why can QUIC survive a change of the client's IP address when TCP cannot?

Basics: connections, encryption and why transport changed

A connection is shared state at both ends (sequence numbers, windows, keys). Setting it up costs round trips; each round trip costs one RTT of waiting. On a 100 ms path, every extra handshake round trip is a visible delay.

What TLS adds, in plain words

TLS makes a connection private and authenticated. The client and server agree on a shared secret key using public-key cryptography (a key exchange), the server proves its identity with a certificate signed by an authority the client trusts, and then both encrypt traffic with the shared key using fast symmetric ciphers. TLS 1.3 needs one round trip for all of this; TLS 1.2 needed two.

What is head-of-line blocking?

TCP presents one ordered byte stream. If segment 7 is lost, segments 8, 9 and 10 may have arrived, but the application cannot see them until 7 is retransmitted (at least one extra RTT). When 10 web objects share one TCP connection, the loss of one packet stalls all 10. The first lab quantifies this.

Why QUIC runs over UDP

New transports cannot run directly over IP because firewalls and NATs drop unknown protocols. UDP passes everywhere, and QUIC implements reliability, congestion control and encryption in the application, so browsers and servers can update the transport as software. Cost: more CPU (no kernel offload, though this is improving) and some networks rate-limit UDP.

Self-check

How many round trips before the first byte of an HTTPS request with TCP + TLS 1.3? (TCP handshake 1, TLS 1, request/response 1: 3.) Why is a stream the right unit for ordering?

Why a new transport

TCP is implemented in kernels and inspected by middleboxes, so extensions (TFO, MPTCP) deploy slowly: ossification. QUIC (Langley et al. 2017; RFC 9000) runs over UDP in user space with encrypted headers, so applications ship transport changes with a library update.

Handshake cost

With RTT as the unit, time to first response byte is

TCP + TLS 1.2 = 4 RTT, TCP + TLS 1.3 = 3 RTT, QUIC = 2 RTT, QUIC 0-RTT = 1 RTT
At RTT 150 ms (mobile or intercontinental) QUIC 1-RTT saves 300 ms versus TCP+TLS 1.2. 0-RTT data is replayable, so only idempotent requests may use it.

Head-of-line blocking

HTTP/2 multiplexes streams over one TCP connection, but a single lost segment stalls every stream behind it. QUIC treats streams independently: loss stalls only the stream whose packet was lost. Connection IDs allow migration across networks (Wi-Fi to LTE) without a new handshake. Google reported meaningful latency gains at the tail (95th-percentile search latency) rather than the median.

Multipath

MPTCP and multipath QUIC send over several paths simultaneously for bandwidth and resilience; the open problems are coupled congestion control (fairness at a shared bottleneck) and scheduling over heterogeneous RTTs.

Loss recovery in QUIC

Packet numbers in QUIC never repeat, so there is no retransmission ambiguity (a classic TCP RTT-sampling problem); lost data is resent in new packets. ACK frames carry ranges, loss detection uses packet and time thresholds, and a probe timeout (PTO) replaces the RTO (RFC 9002). Flow control operates per stream and per connection.

Quantifying head-of-line blocking

If each packet is lost independently with probability p, the chance that a burst of n packets contains at least one loss is

1 − (1 − p)ⁿ
Worked example: p = 1% and n = 100 in flight: 1 − 0.99¹⁰⁰ = 63%. With HTTP/2 over TCP, in most such windows every multiplexed stream pauses until the lost segment is retransmitted (about one RTT); with QUIC only the affected stream waits.

TLS 1.3 and HTTP/3

TLS 1.3 needs one round trip: the client sends its key share in ClientHello, the server replies with its share, certificate and Finished, and application data follows. Forward secrecy is mandatory. HTTP/3 (RFC 9114) maps HTTP semantics onto QUIC streams and replaces HPACK with QPACK to avoid header-compression blocking.

Common pitfalls

Assuming QUIC is always faster (on clean low-RTT links the gain is small and user-space CPU cost is higher), blocking UDP 443 so browsers fall back silently, and forgetting that 0-RTT is replayable.

Advanced: the TLS 1.3 handshake and key schedule

ClientHello carries the supported cipher suites and one or more key shares (e.g., X25519). ServerHello selects a suite and returns its key share; from the resulting shared secret both sides derive handshake keys with HKDF. The rest of the server flight (EncryptedExtensions, Certificate, CertificateVerify, Finished) is already encrypted, hiding the certificate from passive observers. The client verifies the chain and signature, sends Finished, and both derive application traffic keys. Properties: forward secrecy for every connection (ephemeral Diffie-Hellman), removal of weak or legacy primitives, and one RTT cost. Session resumption uses a pre-shared key from a ticket; with 0-RTT, the client sends early data in its first flight, encrypted under the resumption key. Early data is replayable (no fresh server randomness), so servers must restrict it to idempotent requests and may use single-use tickets or time windows.

Advanced: QUIC in depth

Packets and frames. Long headers (Initial, Handshake, 0-RTT, Retry) carry version and connection IDs during setup; short headers carry only the destination connection ID. Payload is a sequence of frames (STREAM, ACK, CRYPTO, MAX_DATA, MAX_STREAM_DATA, NEW_CONNECTION_ID, PATH_CHALLENGE ...). Nearly all of it is authenticated and encrypted; packet numbers are protected by header protection.

Streams and flow control. Each stream is an independent ordered byte stream with its own credit (MAX_STREAM_DATA) plus a connection-level credit (MAX_DATA), so a slow stream cannot exhaust the connection's buffer. Unidirectional and bidirectional streams are created implicitly by use.

Loss detection and congestion control (RFC 9002). Packet numbers never repeat, which removes retransmission ambiguity and allows precise RTT samples including the peer's reported ack delay. A packet is declared lost if a later packet was acknowledged and it is more than 3 packet numbers older or older than 9/8 × max(SRTT, latest RTT). The PTO timer sends probe packets when no ACK arrives. The specification defines a NewReno-style controller; implementations commonly use CUBIC or BBR, pacing and HyStart++. Because congestion control is user-space code, deployments can run different algorithms per connection or per CDN and iterate quickly.

Addresses, migration and amplification. A connection is identified by connection IDs rather than the 4-tuple, so a client moving from Wi-Fi to LTE can continue after path validation (PATH_CHALLENGE/RESPONSE). Until the client's address is validated the server may send at most 3× the bytes received, defeating reflection abuse; Retry packets and address-validation tokens add stateless validation. Key update lets endpoints rotate keys without a new handshake. DPLPMTUD probes path MTU, and the spin bit allows passive RTT measurement by on-path observers who opt in.

HTTP/3 and the ecosystem. HTTP/3 maps requests to QUIC streams and uses QPACK, a header compression scheme designed to avoid head-of-line blocking between header blocks. Extensions include WebTransport, MASQUE (proxying UDP and IP over HTTP/3) and DATAGRAM frames for unreliable data. Operationally, QUIC hides transport signals from middleboxes, so operators lose some visibility and must rely on endpoint telemetry, qlog traces and the spin bit.

Measured effects. Reported deployments show the largest gains in tail latency, on lossy or high-RTT networks and for repeat visits via 0-RTT, and smaller gains at the median on good networks; user-space CPU cost is higher than kernel TCP, which is an active area of optimisation (UDP GSO, sendmmsg, kernel-bypass).

Advanced: multipath transport

MPTCP (RFC 8684) lets one connection use several subflows (e.g., Wi-Fi and cellular), with a data-sequence mapping above the subflow sequence spaces. Coupled congestion control (LIA, OLIA, BALIA) ensures that a multipath flow is no more aggressive than a single TCP flow at any shared bottleneck, while shifting traffic towards less congested paths. Schedulers choose which subflow carries each segment; the min-RTT default can suffer from head-of-line blocking when RTTs differ greatly, motivating redundant and blocking-estimation schedulers. Multipath QUIC applies the same ideas with per-path packet number spaces. Open problems: energy cost of keeping radios active, middlebox interference with options, and fairness at shared bottlenecks.

Advanced: reading a QUIC connection end to end

A typical first connection proceeds as follows. The client sends an Initial packet (padded to at least 1,200 bytes to limit amplification) carrying a CRYPTO frame with the TLS ClientHello; Initial packets are protected with keys derived from the destination connection ID and a version-specific salt, so anyone on the path can read them (this is intentional: it lets load balancers route by SNI/connection ID). The server replies with an Initial (ServerHello) and Handshake packets (the encrypted remainder of its flight). The client completes the handshake and may now send 1-RTT data. The server confirms the handshake and sends HANDSHAKE_DONE; both discard Initial and Handshake keys. Application data then flows in short-header packets. Debugging uses a TLS key log (SSLKEYLOGFILE) so Wireshark can decrypt, or qlog files from the endpoints visualised with qvis, which show packets sent, lost, acknowledged and congestion-window evolution.

Advanced: scheduling streams and priorities

Streams share one congestion window, so an endpoint must decide which stream's data to send next. Simple round-robin gives every stream an equal share (good fairness, but delays a small critical resource, e.g. a stylesheet, behind large images). Browsers therefore declare priorities: HTTP/2's dependency tree proved complex and inconsistently implemented; HTTP/3 uses Extensible Priorities (RFC 9218), a urgency level from 0 to 7 plus an incremental flag that says whether partial data is useful (progressive images) or the object is only useful when whole (scripts). Servers should send higher urgency first and share bandwidth among equal urgency flows; implementation quality varies, which is a major source of page-load differences between servers.

Advanced: flow control and receiver tuning

Per-stream and per-connection credit limit how much a sender may transmit. A receiver that advertises too little throttles the sender to window/RTT (see the BDP lab); one that advertises too much risks memory exhaustion (a denial-of-service lever). Implementations auto-tune: they grow the advertised window when the sender repeatedly fills it, typically by doubling each time the application drains the buffer within about two RTTs. Because limits are per stream, a stalled consumer on one stream cannot starve others unless the connection limit is exhausted, so servers cap per-stream and total buffered data.

Advanced: congestion control and pacing inside QUIC

QUIC implementations pace packets: sending a whole window back to back creates microbursts that overflow shallow buffers. A typical pacer spreads the congestion window over the smoothed RTT, with rate = N · cwnd / smoothed_rtt (N ≈ 1.25 allows the window to grow during slow start). Because the transport lives in user space, operators run CUBIC, BBR or custom controllers per connection and deploy updates in days. Hybrid slow start (HyStart++) leaves slow start when RTT begins to rise, avoiding massive overshoot. Loss detection is precise because packet numbers are never reused; the loss-time threshold (9/8 of the larger of smoothed and latest RTT, printed in Lab 6.4) lets QUIC recover from reordering without spurious retransmission, and persistent congestion (a long run of lost packets spanning multiple PTOs) collapses the window to its minimum.

Advanced: CPU cost and engineering

Kernel TCP benefits from decades of offloads: segmentation offload, checksum offload and zero-copy sends. User-space QUIC starts at a disadvantage: per-packet system calls and encryption in software. Mitigations: UDP generic segmentation offload (send one large buffer split by the NIC or kernel into many datagrams), sendmmsg/recvmmsg batching, GRO on receive, hardware AES offload, io_uring, and in extreme cases kernel-bypass stacks. Server operators report significantly higher CPU for QUIC than for TCP in early deployments, narrowing as these optimisations land, so HTTP/3 rollouts need capacity planning.

Advanced: deployment, discovery and failure modes

Clients usually do not know a server speaks HTTP/3. Discovery uses an Alt-Svc HTTP header (the server announces that h3 is available) or the DNS HTTPS/SVCB record (which also carries ALPN and IP hints, allowing first-visit QUIC). Because some networks block or throttle UDP, clients race QUIC against TCP ('happy eyeballs') and fall back when QUIC fails, so measured benefits depend on the mix of networks. Middlebox behaviour matters: NAT bindings for UDP expire quickly (often 30 s), so endpoints send keep-alives; some enterprise firewalls drop unknown UDP; and carrier-grade NATs may rebind ports, which connection IDs and path validation handle. Measurement studies (Kakhki et al. 2017; Yu et al. 2021) found that gains vary with implementation quality, network conditions and workload, and that mis-tuned QUIC stacks can underperform TCP, so evaluate with the same congestion controller on both.

Advanced: what to measure

Compare protocols on page load time, time to first byte, speed index, rebuffering for video, and especially the 95th and 99th percentiles; control for the congestion controller, initial window, server location and TLS resumption; run repeated paired trials in time; and always report the number of requests and the network emulation parameters. Lab 6.1: Measuring head-of-line blocking

10 streams of 30 packets are interleaved on one connection (window 20 packets per RTT, random loss p). A packet is usable by the application only when every earlier packet in its ordering domain has arrived: the whole connection for TCP/HTTP/2, only its own stream for QUIC. The head-of-line (HOL) delay is usable time minus arrival time, in RTTs.

import random
def hol_delays(p, mode, streams=10, size=30, W=20, seed=0):
    rnd = random.Random(seed)
    order = [(s, i) for i in range(size) for s in range(streams)]      # round-robin interleaving
    n = len(order); recv = [None] * n; pending = list(range(n)); r = 0
    while pending:
        r += 1
        send, pending = pending[:W], pending[W:]
        lost = [k for k in send if rnd.random() < p]
        for k in send:
            if k not in lost: recv[k] = r
        pending = lost + pending                                       # retransmit lost packets first
    run, out = {}, []
    for k, (s, i) in enumerate(order):
        dom = None if mode == "tcp" else s                             # ordering domain
        run[dom] = max(run.get(dom, 0), recv[k]); out.append(run[dom] - recv[k])
    return out
print("loss  mode   mean HOL delay   share of packets delayed   p95 delay (RTTs)")
for p in (0.01, 0.03, 0.05):
    for mode in ("tcp", "quic"):
        d = sum((hol_delays(p, mode, seed=s) for s in range(120)), []); d.sort()
        print(f"{p:4.0%}  {mode:5s} {sum(d)/len(d):12.3f} {sum(x > 0 for x in d)/len(d):18.1%} {d[int(0.95*len(d))]:20d}")

Lab 6.2: ACK ranges and the probe timeout

QUIC acknowledges ranges of packet numbers, and its probe timeout (RFC 9002) is PTO = SRTT + max(4·RTTVAR, 1 ms) + max_ack_delay, doubling on each consecutive PTO.

def ack_ranges(pns):
    pns = sorted(set(pns)); out = []; s = prev = pns[0]
    for x in pns[1:]:
        if x != prev + 1: out.append((s, prev)); s = x
        prev = x
    out.append((s, prev)); return out[::-1]                  # largest range first, as in an ACK frame
print("received 1,2,3,5,6,9 ->", ack_ranges([1, 2, 3, 5, 6, 9]))
srtt, rttvar, mad = 0.100, 0.020, 0.025
pto = srtt + max(4 * rttvar, 0.001) + mad
print("PTO =", round(pto * 1000), "ms; after 3 consecutive PTOs:", [round(pto * 2**k * 1000) for k in range(3)], "ms")
print("amplification limit: server may send", 3 * 1200, "bytes in reply to a 1200-byte Initial")

Lab 6.3: QUIC variable-length integers and stream IDs

QUIC encodes integers in 1, 2, 4 or 8 bytes; the two top bits of the first byte give the length. The sample values are the examples in RFC 9000 Appendix A. Stream IDs carry the initiator and direction in their two low bits.

def enc_varint(v):
    for n, tag in ((1, 0), (2, 1), (4, 2), (8, 3)):
        if v < (1 << (8 * n - 2)): return ((tag << (8 * n - 2)) | v).to_bytes(n, "big")
    raise ValueError("too large")
def dec_varint(b):
    n = 1 << (b[0] >> 6); return int.from_bytes(b[:n], "big") & ((1 << (8 * n - 2)) - 1), n
tests = [("c2197c5eff14e88c", 151288809941952652), ("9d7f3e7d", 494878333), ("7bbd", 15293), ("25", 37)]

Lab 6.4: The QUIC RTT estimator, probe timeout and loss threshold

RFC 9002: the first sample sets smoothed_rtt = sample and rttvar = sample/2; later samples subtract the peer's ack delay when that keeps the result above the minimum RTT. PTO = smoothed_rtt + max(4·rttvar, 1 ms) + max_ack_delay and doubles on each consecutive PTO. A packet is declared lost when older than 9/8·max(smoothed, latest) RTT.

class Rtt:
    def __init__(self): self.srtt = None; self.var = None; self.min = float("inf")
    def sample(self, latest, ack_delay=0.0):
        self.min = min(self.min, latest)
        adj = latest - ack_delay if latest >= self.min + ack_delay else latest
        if self.srtt is None: self.srtt, self.var = latest, latest / 2
        else:
            self.var = 0.75 * self.var + 0.25 * abs(self.srtt - adj)
            self.srtt = 0.875 * self.srtt + 0.125 * adj
    def pto(self, mad=25.0, backoff=0): return (self.srtt + max(4 * self.var, 1.0) + mad) * 2 ** backoff
r = Rtt()
print("sample(ms) ack_delay  srtt    rttvar   PTO   loss-time threshold")
for latest, ad in ((120, 0), (100, 10), (110, 5), (300, 0), (105, 5)):
    r.sample(latest, ad)
    print(f"{latest:9d} {ad:9d} {r.srtt:7.1f} {r.var:8.1f} {r.pto():7.1f} {9/8*max(r.srtt, latest):10.1f}")
print("PTO backoff after 3 timeouts:", [round(r.pto(backoff=k)) for k in range(4)], "ms")

Lab 6.5: HKDF (RFC 5869) and a toy Diffie-Hellman exchange

TLS 1.3 and QUIC derive every key with HKDF-Extract and HKDF-Expand. This lab checks our implementation against RFC 5869 test case 1, derives labelled keys the way the TLS 1.3 key schedule does (with simplified labels), and runs Diffie-Hellman with tiny numbers.

import hmac, hashlib
def extract(salt, ikm): return hmac.new(salt, ikm, hashlib.sha256).digest()
def expand(prk, info, L):
    out, t, i = b"", b"", 1
    while len(out) < L:
        t = hmac.new(prk, t + info + bytes([i]), hashlib.sha256).digest(); out += t; i += 1
    return out[:L]
prk = extract(bytes(range(13)), bytes([0x0b]) * 22)
okm = expand(prk, bytes(range(0xf0, 0xfa)), 42)
print("RFC 5869 test case 1, PRK matches:", prk.hex() == "077709362c2e32df0ddc3f0dc47bba6390b6c73bb50f9c3122ec844ad7c2b3e5")
print("RFC 5869 test case 1, OKM matches:", okm.hex() == "3cb25f25faacd57a90434f64d0362f2a2d2d0a90cf1a5a4c5db02d56ecc4c5bf34007208d5b887185865")
p, g, a, b = 23, 5, 6, 15
A, B = pow(g, a, p), pow(g, b, p)

Exercises

Exercise 1: Why can middleboxes block deployment of a new TCP option but not a new QUIC feature?

TCP headers are visible and parsed; QUIC encrypts nearly everything above UDP, leaving middleboxes nothing to drop selectively.

Exercise 2: What attack does 0-RTT enable and how do servers limit it?

Replay of early data. Servers restrict 0-RTT to idempotent requests and use anti-replay caches or single-use tickets.

Exercise 3: p = 0.5%, 40 packets in flight. P(at least one loss)?

1 − 0.995⁴⁰ = 1 − 0.818 = 18.2%.

Exercise 4: Why does QUIC encrypt packet headers' transport fields?

To prevent middleboxes from depending on, or modifying, them: this keeps the protocol evolvable (anti-ossification) and hides metadata.

Exercise 5: SRTT = ⅞·SRTT + ⅛·R with SRTT = 100 ms and sample R = 180 ms. New SRTT?

87.5 + 22.5 = 110 ms.

Exercise 6: QUIC's server may send at most 3× the bytes it received before validating the client. A client Initial is padded to 1200 B. Server limit?

3600 bytes.

Exercise 7: Decode the QUIC variable-length integer 0x7bbd and encode 37.

0x7bbd: top bits 01 → 2 bytes; clear them: 0x3bbd = 15,293. 37 < 64 → one byte 0x25.

Exercise 8: Stream ID 6, 5 and 4: who initiated them and are they bidirectional?

6 = ...10 → client-initiated unidirectional; 5 = ...01 → server-initiated bidirectional; 4 = ...00 → client-initiated bidirectional.

Exercise 9: QUIC RTT estimator: first sample 120 ms, second sample 100 ms with ack delay 10 ms. smoothed RTT, rttvar and PTO (max_ack_delay 25 ms)?

First: srtt 120, var 60. Second: min = 100, 100 < 100 + 10 so no ack-delay adjustment; var = ¾·60 + ¼·|120−100| = 50; srtt = ⅞·120 + ⅛·100 = 117.5. PTO = 117.5 + 4·50 + 25 = 342.5 ms.

Exercise 10: Why does the receive window cap a 100 ms path at about 5 Mb/s when it is 64 KB?

Throughput ≤ window/RTT = 65,536 × 8 / 0.1 s ≈ 5.2 Mb/s.

Exercise 11: At RTT 80 ms how much faster is the first byte with QUIC 1-RTT than with TCP+TLS 1.2?

TCP+TLS 1.2 needs 4 RTT = 320 ms; QUIC 1-RTT needs 2 RTT = 160 ms; it saves 160 ms.

Exercise 12: Why must the 'Initial' packet be padded to 1,200 bytes?

To bound amplification: the server may answer with at most 3× the bytes received before validating the client, so a larger client packet allows a useful server flight and a spoofed small request cannot cause large reflection.

Key takeaway

TTFB = k·RTT ; k = 4, 3, 2, 1
