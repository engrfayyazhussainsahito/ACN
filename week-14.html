Basics: the numbers you need to reason about AI clusters

Sizes

A model with P parameters stored in 16-bit format takes 2P bytes; a 70-billion-parameter model's gradients are 140 GB. Training also stores optimiser state (often 8 to 16 bytes per parameter) and activations, which is why one GPU (80 GB-class memory) cannot hold a large model and the work is split. The compute per training step is approximately 6 × P × (tokens in the batch) floating-point operations (2 for the forward pass, 4 for the backward pass), which fixes the compute time for a given number of GPUs and their sustained speed. Lab 14.3 uses exactly this.

A step in the life of one GPU

  1. Receive a microbatch of tokens. 2. Compute the forward pass layer by layer (tensor-parallel layers need an all-reduce after some operations). 3. Send activations to the next pipeline stage. 4. Compute the backward pass in reverse, producing gradients. 5. All-reduce gradients with data-parallel peers (overlapped with step 4 where possible). 6. Update parameters. The network appears in steps 2, 3 and 5, and each uses a different pattern and a different part of the fabric.

Four network tiers

RDMA verbs in one picture

An application registers memory with the NIC, creates a queue pair (a send queue and a receive queue), and posts work requests (send, receive, RDMA write, RDMA read) to it. The NIC executes them and posts completion entries to a completion queue that the application polls, with no system call on the fast path. One-sided operations (RDMA write/read) touch remote memory without involving the remote CPU. RoCEv2 packets are Ethernet + IP + UDP (port 4791) + a 12-byte base transport header + payload + ICRC; Lab 14.4 shows the resulting efficiency (about 98% for 4 KB payloads, 76% for 256 B).

Why a lossless network?

Early RDMA NICs recovered from loss by go-back-N: on a gap the sender resends everything after the lost packet. With thousands of packets in flight, even a 10⁻⁴ loss rate wastes a few percent of capacity, and a larger rate collapses throughput, so operators built lossless Ethernet using priority flow control (PFC): a switch whose queue is nearly full sends a pause frame upstream so no packet is dropped. The price is that pauses propagate: a congested port can block unrelated flows sharing the upstream queue (head-of-line blocking), and cyclic dependencies can deadlock (Lab 14.5).

Self-check

Roughly how many FLOPs does a step with a 7 B-parameter model and a 1 M-token batch need? (6 × 7×10⁹ × 10⁶ = 4.2×10¹⁶.) Which parallelism needs the fastest links? Why is a lost packet more costly with go-back-N than with selective retransmission?

Basics: how a neural network gets trained on many machines

Training adjusts a model's parameters (billions of numbers) to reduce an error. One step takes a batch of data, computes a prediction error (forward pass), computes how each parameter should change (backward pass, giving gradients) and updates the parameters. A single GPU is far too slow for large models, so many GPUs work together.

Parallelism in one paragraph each

  • Data parallelism: every GPU holds a full copy of the model and processes different data. After the backward pass the GPUs must average their gradients so all copies stay identical: this is an all-reduce over the gradient size.
  • Tensor (model) parallelism: one layer's matrices are split across GPUs; partial results are combined at every layer, so communication happens many times per step and needs very high bandwidth.
  • Pipeline parallelism: consecutive layers sit on different GPUs and activations flow between them (point-to-point).
  • Expert parallelism (mixture of experts): tokens are routed to experts on other GPUs, an all-to-all exchange.

All-reduce equals reduce-scatter followed by all-gather, which is exactly why the ring algorithm sends 2·S·(N−1)/N bytes.

What is RDMA?

Normal networking passes through the operating system: system calls, copies and interrupts cost microseconds and CPU. Remote direct memory access lets the network card read and write application memory directly, bypassing the kernel (kernel bypass) and avoiding copies (zero copy). The application posts work requests to queue pairs; the NIC does the rest. InfiniBand is a complete RDMA-native network; RoCEv2 carries RDMA over UDP/IP so it works on Ethernet.

Why the network matters so much

If computing a step takes 100 ms and communicating takes 40 ms, with no overlap the step takes 140 ms: scaling efficiency 71%. With perfect overlap it stays 100%. As models and cluster sizes grow, communication is the part that does not shrink, so cluster networks became a first-class design problem. In the second lab you can compute the efficiency for different communication times.

Self-check

Why is all-reduce the same as reduce-scatter plus all-gather? Why does tensor parallelism need a faster network than data parallelism? (It communicates every layer rather than once per step.)

Why AI traffic is different

Training is synchronous: after each step every GPU must combine its gradients with all others (an all-reduce) before the next step can start. So (1) the slowest flow sets the step time, making tail latency the metric that matters; (2) traffic consists of few, huge, long-lived flows rather than millions of short ones, so ECMP hashing has very low entropy; (3) all GPUs communicate at the same instant, which creates synchronised bursts and incast-like patterns.

Cost model of all-reduce

Let N GPUs each hold S bytes, with per-GPU bandwidth B and per-step latency α. Ring all-reduce has two phases. Reduce-scatter takes N−1 steps, each moving S/N bytes per GPU; all-gather takes another N−1 steps of the same size. Therefore

T_ring = 2(N−1)/N · S/B + 2(N−1)·α

The bandwidth term approaches 2S/B and is optimal (Patarasuk and Yuan 2009): no algorithm can move less data per GPU. Recursive halving-doubling keeps the same bandwidth term but needs only 2·log₂N steps:

T_rhd = 2(N−1)/N · S/B + 2·log₂(N)·α
Worked example: a 5-billion-parameter model has 10 GB of fp16 gradients. With N = 64 and B = 50 GB/s (400 Gb/s per GPU), T_ring = 2·(63/64)·10/50 s = 0.394 s plus 0.63 ms of latency. For a tiny 1 MB message with N = 1024, ring needs 10.2 ms of latency while halving-doubling needs 0.1 ms.

RDMA and RoCEv2

Remote direct memory access moves data NIC-to-NIC without involving the CPU, giving microsecond latency. RoCEv2 carries it over UDP/IP on Ethernet. Original RoCE NICs used go-back-N retransmission, so a single loss re-sends a whole window; a first-order model gives goodput efficiency ≈ 1/(1 + p·W) for loss rate p and window W packets. They therefore rely on a lossless fabric: priority flow control (PFC) pauses the upstream hop before the buffer overflows. PFC brings its own problems: head-of-line blocking, pause storms, and deadlocks when a cyclic buffer dependency forms (Guo et al. 2016).

Congestion control for RDMA

DCQCN (Zhu et al. 2015) combines ECN marking at switches with rate-based reaction at senders: on receiving congestion notification packets the sender cuts its rate multiplicatively and then recovers in stages. HPCC uses in-band telemetry to read queue lengths and link utilisation directly. Receiver-driven schemes (Homa, NDP) and Ultra Ethernet's packet spraying aim for the same goals without PFC.

Topology

GPU clusters use full-bisection fat-trees or Clos fabrics, often rail-optimised: the i-th NIC of every server connects to the i-th leaf switch ("rail i"), so collectives among corresponding GPUs stay within one leaf. Within a server, NVLink/NVSwitch provides several hundred GB/s between GPUs, so hierarchical collectives first reduce within the server, then across the network. Dragonfly and torus topologies are used in other systems (supercomputers, TPU pods) trading cost for locality.

Worked example: hashing 8 equal elephant flows onto 8 equal-cost links gives P(no two collide) = 8!/8⁸ = 0.24%, so a collision is almost certain and a collided link runs at half rate, halving the whole collective. Remedies: flowlet or per-packet load balancing, many more queue pairs per connection, or explicit path control.

Common pitfalls

Using the average link utilisation to judge a fabric (collectives care about the worst link), enabling PFC without deadlock analysis, ignoring the host side (PCIe, NIC buffers) and assuming network bandwidth is the only bottleneck when compute and communication can overlap.

Advanced: collective algorithms in practice

Libraries such as NCCL choose among ring (bandwidth-optimal; latency grows with N), tree and double binary tree (latency grows with log N; two complementary trees keep every link busy in both directions), and halving-doubling (log N steps; best for power-of-two N) depending on message size, topology and GPU count; small messages favour trees, large messages rings. Hierarchical algorithms exploit the bandwidth hierarchy: reduce-scatter inside the server over NVLink-class links, run the inter-server all-reduce on only 1/g of the data over g parallel rails, then all-gather inside the server; the first lab shows a speed-up of roughly 4× at every scale for g = 8, because the slow network carries only 1/g of the data per link and the fast intra-server phases are cheap. In-network reduction (e.g. NVIDIA SHARP and similar) lets switches perform the summation, cutting the data each GPU sends and receives from 2S to S and the number of steps to the tree depth, at the cost of switch memory and software complexity.

Advanced: mapping parallelism to topology

Bandwidth is tiered: inside a server GPUs share a high-bandwidth NVLink/NVSwitch domain (hundreds of GB/s); across servers each GPU has its own NIC (e.g. 200 to 800 Gb/s); across racks the fabric may be oversubscribed. A common placement puts tensor parallelism inside the NVLink domain, pipeline stages across servers in one rack or pod, and data parallelism across the rest so that the large but infrequent gradient all-reduce crosses the thinnest links. All-to-all in mixture-of-experts models has no locality to exploit and stresses bisection bandwidth. Rail-optimised topologies attach the i-th NIC of every server to the i-th leaf switch so that collectives among GPUs with the same local index never cross spines; the price is that traffic between different rails does cross spines or relies on intra-server forwarding.

Advanced: congestion control and load balancing for training fabrics

Training generates few long synchronised flows: ECMP hashing has too little entropy (see the second lab where splitting flows into sub-flows drives the busiest-link overload toward 1), and a single slow link delays the whole collective (stragglers). Solutions combine: more queue pairs per connection and path-aware flowlet or per-packet spraying (InfiniBand adaptive routing, Ultra Ethernet Consortium's packet spraying with out-of-order delivery support in the NIC), receiver-driven or credit-based transports, congestion control driven by ECN (DCQCN), RTT/delay (Swift-like, TIMELY) or in-band telemetry (HPCC), and sometimes no congestion control within carefully scheduled collectives. Lossless Ethernet needs priority flow control (PFC) with deadlock avoidance; PFC storms and head-of-line blocking motivate designs that avoid PFC or confine it to a single hop. Scale-out designs also address failure: with tens of thousands of links, flaps are routine, so fast rerouting, link health monitoring and job restart with checkpoints become part of network design.

Advanced: optical circuit switching and alternative topologies

Torus and mesh topologies (3-D torus in TPU pods) offer excellent nearest-neighbour bandwidth at low cost; optical circuit switches can reconfigure which racks connect, letting the same hardware form different slice shapes and routing around failures (reported for TPU v4 superpods). The cost is reconfiguration time (milliseconds), so circuits are changed between jobs or phases rather than per packet. Research directions include photonics inside packages, co-designed collective algorithms and topologies, and rethinking transports for collectives rather than flows.

Advanced: reasoning about scale

Scaling efficiency η = T_compute / (T_compute + T_exposed_comm). Overlapping communication with the backward pass (bucketed gradient all-reduce while earlier layers are still computing) reduces exposed communication; compression, gradient accumulation, and larger batch sizes reduce its frequency. Latency matters when messages are small (many short collectives per step); bandwidth matters for large gradients. The model T = 2(N−1)/N·S/B + 2(N−1)·α captures both, which is why the ring is best for large S and trees for small S.

Advanced: the training-step budget in detail

Lab 14.3 builds an explicit model. Compute time = 6·P·tokens/(N·F). Tensor parallelism of degree t performs, per layer and microbatch, two all-reduces in the forward pass and two in the backward pass, each over an activation tensor of seq·h·bytes (one sequence per microbatch here), so its traffic per GPU is (L/p)·m·4·2(t−1)/t·seq·h·bytes with m microbatches; because this is frequent and on the critical path, it must stay inside the fast intra-server domain. Pipeline parallelism sends one activation tensor forward and one gradient backward per microbatch per stage boundary, and idles during the pipeline bubble, a fraction (p−1)/m of compute for m microbatches (interleaved schedules reduce it). Data parallelism all-reduces the gradient shard of P/(t·p) parameters among d replicas, once per step, and can overlap with the backward pass. Reading the lab's table: for this configuration compute dominates, tensor-parallel traffic is the largest communication term yet stays on the fast links, and data-parallel traffic over the fabric is small per step; but if the fabric were slower, shrinking the number of GPUs per replica group, or the model's width, changes the balance. The principal design rule: map the most frequent, largest collectives to the fastest links and reserve the oversubscribed fabric for infrequent traffic.

Advanced: sharded data parallelism and memory-driven communication

Data parallelism replicates the whole model on each GPU, which wastes memory. Sharded schemes (ZeRO, fully-sharded data parallel) split optimiser state, gradients and parameters across the data-parallel group, then all-gather parameters just before use and reduce-scatter gradients just after. Communication volume rises to about 1.5× that of plain data parallelism (an all-gather in the forward pass, another in the backward pass, plus a reduce-scatter), but memory per GPU falls roughly in proportion to the group size, enabling larger models. Network consequence: many medium-sized collectives instead of one large all-reduce, so latency and overlap quality matter more.

Advanced: mixture-of-experts and all-to-all

In mixture-of-experts layers each token is routed to a few experts held on different GPUs, requiring an all-to-all before and after the expert computation, per layer, in both passes. All-to-all has no locality: each GPU sends a distinct slice to every other GPU, so traffic crosses the full bisection of the fabric and is sensitive to load imbalance (a popular expert becomes a hotspot and an incast target). Mitigations: capacity factors and auxiliary balancing losses in the model, hierarchical all-to-all (aggregate by node first), placing expert groups within a rail or pod, and overlapping communication with computation by chunking.

Advanced: congestion control for RDMA in more detail

In DCQCN, switches mark packets with ECN when the queue exceeds a threshold; the receiver NIC reflects marks as congestion notification packets (CNPs); the sender's reaction point cuts its rate, keeps an EWMA α of recent congestion, then raises its rate in three phases (fast recovery towards the previous target, additive increase, hyper increase). Lab 14.6 simulates a simplified version, showing the multiplicative cut α/2 and the recovery. Known issues include sensitivity to parameters (the marking thresholds and timers must be tuned to link speed and RTT), unfairness when flows have different RTTs, and slow convergence at 400 Gb/s and beyond. Alternatives: TIMELY (RTT-gradient rate control), HPCC (uses in-band telemetry to compute the exact inflight bytes per link), Swift (delay targets, host plus fabric), receiver-driven protocols (Homa, NDP: the receiver paces senders with credits or pulls, and switches may trim payloads on overflow, keeping headers), and the Ultra Ethernet design of packet-sprayed multipath transports with selective retransmission. Whatever the scheme, the fabric's load balancing and congestion control interact: per-packet spraying removes hash collisions but reorders packets, so the transport needs out-of-order tolerance.

Advanced: PFC deadlock, storms and mitigation

A deadlock needs a cyclic buffer dependency (CBD). In a Clos fabric routed strictly up then down there is no cycle, but link failures or misconfigurations can force packets to go down, up and down again, creating one (Lab 14.5's second graph). A pause storm occurs when a faulty NIC keeps sending pause frames: the pause propagates upstream and can freeze large parts of the fabric. Mitigations: watchdogs that drop packets or disable PFC on a queue stuck paused for too long, routing that forbids valleys, separate priority classes for different path stages (rotating the priority at each valley), limiting PFC to the first hop (ToR-to-NIC) and relying on end-to-end congestion control and fast loss recovery elsewhere, and, for new designs, avoiding PFC through selective retransmission and trimming.

Advanced: sizing the fabric and its cost

Lab 14.7 computes sizes: with 64-port switches a non-blocking two-tier fabric reaches 2,048 endpoints and a three-tier one 65,536, needing 5,120 switches and about 196,608 links (each of which, above the ToR, usually carries two optical transceivers). Optics and cabling dominate cost and failure rates, so designers trade oversubscription (tapering the upper tiers: 2:1 halves the upper-tier switches and links), bandwidth per GPU, and the number of tiers. Rail optimisation keeps same-rail traffic below the spine. Larger radix switches (51.2 Tb/s generations) reduce tiers; co-packaged optics and lower-power links reduce the cost per bit. Failure modelling: with many components the cluster's mean time between failures is the component MTBF divided by the number of components, so a 16,384-GPU job sees a failure every few hours; the checkpoint interval from Young's formula and fast job restart (spare nodes, localised restart, in-memory checkpoints) are essential parts of the design.

Advanced: measuring and operating AI fabrics

Useful signals: collective completion times and their variance across ranks (stragglers), link utilisation at fine granularity, ECN mark and PFC pause counts per queue, retransmission and NIC error counters, and burst statistics. Debugging uses collective-level traces (which rank waited on which peer), synthetic benchmarks (NCCL tests across a sweep of message sizes and GPU counts), and topology-aware health checks that find a single slow cable or misconfigured port before it slows a whole job. Because one slow link slows every GPU, tail behaviour, not average bandwidth, defines usable capacity.

Lab 14.2: Spraying beats hashing for elephants

Eight equal elephant flows share 8 equal-cost links. Split each flow into split independently routed sub-flows (flowlets or packet spraying) and measure how much the busiest link exceeds the ideal load.

import random, collections
def slowdown(flows, links, split, trials=4000, seed=1):
    random.seed(seed); tot = 0.0
    for _ in range(trials):
        c = collections.Counter(random.randrange(links) for _ in range(flows * split))
        tot += max(c.values()) / split / (flows / links)
    return tot / trials
print("sub-flows per flow   busiest link / ideal load (collective slows by this factor)")

Lab 14.3: A training-step budget: compute, tensor, pipeline and data-parallel communication

An illustrative model of one step of a GPT-3-scale training job (175 B parameters, 96 layers, hidden size 12,288, 3.1 M tokens per step) on 1,024 GPUs with 300 TFLOP/s effective per GPU, 300 GB/s inside a server and 50 GB/s per GPU across servers. Tensor parallelism (t) does four all-reduces per layer per microbatch, pipeline parallelism (p) sends activations between stages, data parallelism (d) all-reduces gradients. Memory limits are ignored; this shows where network time goes.

def step(t, p, N=1024, P=175e9, L=96, h=12288, tokens=3.1e6, seq=2048, F=300e12, bw_in=300e9, bw_net=50e9, by=2):
    d = N // (t * p)
    comp = 6 * P * tokens / (N * F)
    mb = tokens / d / seq                                  # microbatches (one sequence each) per replica
    act = seq * h * by                                     # one activation tensor (bytes)
    tp = (L / p) * mb * 4 * (2 * (t - 1) / t) * act / bw_in
    pp = mb * 2 * act / bw_net
    dp = 2 * (d - 1) / d * (P / (t * p) * by) / bw_net
    bubble = comp * (p - 1) / mb
    return d, mb, comp, tp, pp, dp, bubble
print(" t  p   d  microb | compute  TP-comm  PP-comm  DP-comm  pipe-bubble | efficiency if comm not overlapped")
for t, p in ((8, 8), (8, 16), (4, 8), (8, 4)):

Lab 14.5: PFC deadlock: finding cyclic buffer dependencies

With priority flow control a queue cannot drain while the downstream queue it feeds is full and has paused it. Draw an edge X → Y when X waits for room in Y; a cycle means a possible deadlock. Up-then-down (valley-free) routing in a Clos fabric has no cycle; a detour that goes down, up and down again can.

def has_cycle(graph):
    color = {}
    def dfs(u):
        color[u] = 1
        for v in graph.get(u, []):
            if color.get(v) == 1: return True
            if color.get(v) is None and dfs(v): return True
        color[u] = 2; return False
    return any(color.get(u) is None and dfs(u) for u in list(graph))
tree = {"leaf1.up": ["spine1.down"], "spine1.down": ["leaf2.host"], "leaf2.host": []}
bounce = {"leaf1.up": ["spine1.down"], "spine1.down": ["leaf2.up"], "leaf2.up": ["spine2.down"], "spine2.down": ["leaf1.up"]}
print("valley-free routing, cyclic buffer dependency:", has_cycle(tree))
print("down-up-down detour after a link failure, cyclic buffer dependency:", has_cycle(bounce))
Output

Lab 14.6: A simplified DCQCN rate controller

Two flows (starting at 80 and 10 Gb/s) share a 100 Gb/s link. When the aggregate exceeds capacity, flows are marked with probability proportional to their rate and cut their rate by α/2 (α is an EWMA of marks); otherwise they recover towards their target rate and then add a small increment. A fluid caricature of DCQCN: it shows the control law, not hardware timing.

import random
def dcqcn(C=100.0, start=(80.0, 10.0), steps=48000, g=1 / 16, rai=0.02, seed=1):
    rnd = random.Random(seed); rc = list(start); rt = list(start); al = [1.0] * len(rc); st = [0] * len(rc); out = []
    for t in range(steps):
        over = sum(rc) > C
        for i in range(len(rc)):
            if over and rnd.random() < rc[i] / sum(rc):
                rt[i] = rc[i]; rc[i] *= 1 - al[i] / 2; al[i] = (1 - g) * al[i] + g; st[i] = 0
            else:
                al[i] *= 1 - g; st[i] += 1
                if st[i] > 5: rt[i] += rai
                rc[i] = (rc[i] + rt[i]) / 2
        if t % 8000 == 0 or t == steps - 1: out.append((t, [round(x, 1) for x in rc]))
    return out
for t, r in dcqcn(): print(f"step {t:6d}: rates (Gb/s) {r}   total {sum(r):6.1f}")

Lab 14.7: Sizing a GPU fabric and choosing a checkpoint interval

A non-blocking fat-tree built from k-port switches supports k²/2 endpoints with two tiers and k³/4 with three. Large clusters fail often; Young's formula gives the checkpoint interval T = √(2·δ·M) that minimises lost work (δ = checkpoint time, M = cluster mean time between failures).

import math
print("radix  2-tier GPUs  3-tier GPUs  3-tier switches  3-tier links")
for k in (32, 64, 128): print(f"{k:5d} {k*k//2:12d} {k**3//4:12d} {5*k*k//4:15d} {3*k**3//4:13d}")
N, mtbf_gpu_h, ckpt = 16384, 50000.0, 60.0
M = mtbf_gpu_h / N * 3600
T = math.sqrt(2 * ckpt * M)
print(f"{N} GPUs, per-GPU MTBF {mtbf_gpu_h:.0f} h -> cluster MTBF {M/3600:.2f} h")
print(f"checkpoint cost {ckpt:.0f} s: optimal interval {T/60:.1f} min, expected overhead about {math.sqrt(2 * ckpt / M):.1%}")

import math
def ring(N, S, B=50e9, a=5e-6): return 2 * (N - 1) / N * S / B + 2 * (N - 1) * a
def rhd(N, S, B=50e9, a=5e-6): return 2 * (N - 1) / N * S / B + 2 * math.log2(N) * a
print(f"10 GB, N=64 : ring {ring(64, 10e9)*1e3:.1f} ms")
print(f"1 MB, N=1024: ring {ring(1024, 1e6)*1e3:.2f} ms, halving-doubling {rhd(1024, 1e6)*1e3:.2f} ms")

Exercises

Exercise 1: Ring all-reduce, N = 8 GPUs, S = 1 GB, B = 100 GB/s, ignore latency. Time?

2·(7/8)·1/100 s = 17.5 ms.

Exercise 2: Why is halving-doubling better than ring for small messages but not for large ones?

Both have the same bandwidth term; halving-doubling has 2·log₂N latency steps instead of 2(N−1), which only matters when latency dominates.

Exercise 3: A job's 16 GPUs use 4 equal-cost paths with 4 elephant flows. P(no collision)?

4!/4⁴ = 24/256 = 9.4%.

Exercise 4: RoCEv2 with 1,024-byte payloads: wire efficiency?

Overhead 82 B (preamble 8, IFG 12, Ethernet 14, FCS 4, IP 20, UDP 8, BTH 12, ICRC 4): 1024/1106 = 92.6%.

Exercise 5: Gradients of a 70 B-parameter model in 16-bit format are all-reduced with plain data parallelism over a 50 GB/s network (large N, ignore latency). Time?

Gradient size 140 GB; a ring sends ≈ 2×140 GB per GPU; 280/50 = 5.6 s.

Exercise 6: Young's formula with checkpoint time 120 s and cluster MTBF 6 h?

T = √(2 × 120 × 21,600) ≈ 2,277 s ≈ 38 min; overhead ≈ √(2·120/21,600) ≈ 10.5%.

Exercise 7: How many GPUs does a non-blocking 32-port-switch fabric support with two tiers and with three?

k²/2 = 512 and k³/4 = 8,192.

Exercise 8: All-to-all with N = 256 GPUs, 2 GB per GPU, 50 GB/s, ignoring latency?

(255/256) × 2 GB / 50 GB/s ≈ 39.8 ms.

Exercise 9: Why does FSDP/ZeRO increase communication volume by about 1.5× yet remain popular?

It adds a second all-gather of parameters (forward and backward) to the reduce-scatter, but memory per GPU falls roughly by the group size, which lets models fit that otherwise would not.

Key takeaway

T_ring = 2(N−1)/N·S/B + 2(N−1)·α
